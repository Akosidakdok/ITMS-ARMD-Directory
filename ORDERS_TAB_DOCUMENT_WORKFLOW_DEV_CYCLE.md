# Orders Tab Document Workflow — Development Cycle

## 1. Objective

Upgrade the Orders tab to support the complete personnel-order workflow:

```text
Select order series and purpose
        ↓
Upload DOCX or start from a template
        ↓
Enter required fields and personnel
        ↓
Generate the official order number
        ↓
Save as Draft
        ↓
Edit metadata and document
        ↓
Submit for approval
        ↓
Mark as Signed / Released
        ↓
View, filter, download, and audit
```

The implementation must support the required order-number format, DOCX upload, order status tracking, personnel association, filtering, document retrieval, and a defined approach for in-system document editing.

## 2. Current-state assessment

The current Orders module provides:

- Administrative order creation and editing
- Manual order-number entry
- Subject, issued date, effective date, signatory, and description fields
- Personnel association through `personnelIds`
- Record filtering by search, type, personnel, status, and date range
- Award and leave records in the same register
- Browser-based HTML/PDF document templates

The current module does not yet provide:

- GO/SO/LO order series
- The required purpose-code catalog
- Server-generated incremental order numbers
- DOCX upload and storage
- Document versioning
- Signed and draft document lifecycle
- Original DOCX viewing or download
- Reliable in-system Word-document editing
- Document-level audit history

## 3. Functional requirements

### 3.1 Order series

The system must support:

| Code | Description |
|---|---|
| GO | General Order |
| SO | Special Order |
| LO | Letter Order |

### 3.2 Order purpose codes

The system must support the following controlled values:

| Code | Description |
|---|---|
| DES | Designation |
| TDS | Termination of Designation |
| DO | Detail |
| DOX | Extension of Detail |
| TR | Travel |
| RA | Sub-unit Reassignment |
| UA | Unit Reassignment |
| CSC | Combination of Service |
| LV | Leave |
| AW | Award |
| CCS | Change of Civil Status |
| AO | Assignment Order |
| PR | Promotion |
| PA | Appointment |
| RG | Resignation |
| LP | Longevity Pay |
| RCA | Replacement Clothing Allowance |
| SP | Specialist Pay |
| AWOL | Absent Without Leave |
| CN | Change Name |
| CHAPS | Change in Appointed Status |

### 3.3 Order-number format

The official format is:

```text
ITMS-{SERIES}-{PURPOSE}-{YEAR}-{SEQUENCE}
```

Example:

```text
ITMS-SO-DES-2026-0001
```

Order numbers must be generated by the backend and must not be manually editable.

### 3.4 Document statuses

Recommended lifecycle:

```text
Draft → For Approval → Signed → Released → Archived
```

Revocation may occur from `For Approval`, `Signed`, or `Released`:

```text
For Approval → Revoked
Signed       → Revoked
Released     → Revoked
```

Rules:

- Draft records are editable.
- For Approval records are editable only by authorized users.
- Signed records are locked except for controlled administrative corrections.
- Released records are fully locked.
- Archived and Revoked records remain visible for audit purposes.
- Every status change records the actor, timestamp, previous status, new status, and reason.

## 4. Data-model changes

### 4.1 `OrderRecord` additions

Add or formalize these fields in `src/types/pais.ts`:

```ts
type OrderSeries = 'GO' | 'SO' | 'LO';

type OrderPurpose =
  | 'DES' | 'TDS' | 'DO' | 'DOX' | 'TR' | 'RA' | 'UA'
  | 'CSC' | 'LV' | 'AW' | 'CCS' | 'AO' | 'PR' | 'PA'
  | 'RG' | 'LP' | 'RCA' | 'SP' | 'AWOL' | 'CN' | 'CHAPS';

type OrderDocumentStatus =
  | 'Draft'
  | 'For Approval'
  | 'Signed'
  | 'Released'
  | 'Archived'
  | 'Revoked';
```

Recommended fields:

```ts
series: OrderSeries;
purposeCode: OrderPurpose;
purposeLabel: string;
orderNumber: string;
documentStatus: OrderDocumentStatus;
fileName?: string;
fileMimeType?: string;
fileSize?: number;
storagePath?: string;
signedAt?: string;
signedBy?: string;
releasedAt?: string;
releasedBy?: string;
version?: number;
createdBy?: string;
updatedBy?: string;
```

Retain the existing `orderType` field temporarily for backward compatibility, but use `series` and `purposeCode` as the authoritative values for new records.

### 4.2 Sequence table

Use a database-backed sequence table so order numbers remain unique under concurrent saves:

```sql
CREATE TABLE order_sequences (
  year INTEGER NOT NULL,
  series TEXT NOT NULL,
  last_number INTEGER NOT NULL DEFAULT 0,
  PRIMARY KEY (year, series)
);
```

Recommended sequence scope:

- One sequence per year and order series
- Purpose codes share the sequence within the series
- Sequence resets each calendar year

Examples:

```text
ITMS-SO-DES-2026-0001
ITMS-SO-UA-2026-0002
ITMS-GO-AW-2026-0001
```

The sequence increment and order creation should be performed atomically in the backend.

## 6. API design

### Order creation

```text
POST /api/orders
```

Request body should include:

```json
{
  "series": "SO",
  "purposeCode": "DES",
  "subject": "Designation of ITSD Personnel",
  "issuedDate": "2026-09-22",
  "effectiveDate": "2026-10-01",
  "personnelIds": ["p-001", "p-002"],
  "signatory": "PBGEN BENJAMIN H ACORDA",
  "signatoryTitle": "Director, ITMS",
  "documentStatus": "Draft",
  "description": "Designation directives"
}
```

The response should include the generated order number:

```json
{
  "orderNumber": "ITMS-SO-DES-2026-0001",
  "series": "SO",
  "purposeCode": "DES",
  "documentStatus": "Draft"
}
```

### Workflow endpoints

```text
POST /api/orders/:id/submit
POST /api/orders/:id/sign
POST /api/orders/:id/release
POST /api/orders/:id/archive
POST /api/orders/:id/revoke
GET  /api/orders/:id/history
GET  /api/orders/:id/versions
```

Status transitions should be validated by the backend, not only by the frontend.

## 8. Security and permissions

- Only users with management access can create, edit, upload, sign, release, archive, or revoke orders.
- View-only users can view metadata and download documents according to their access level.
- Signed and released documents require server-side authorization checks.
- Uploaded files must be private by default.
- Download URLs must expire.
- Validate file type by both extension and MIME type.
- Enforce file-size limits.
- Sanitize filenames.
- Do not allow arbitrary filesystem paths from the client.
- Record every document access and status change where audit requirements require it.

## 10. Acceptance criteria

The implementation is complete when:

- A user can select GO, SO, or LO.
- A user can select any required purpose code.
- The system generates a valid order number automatically.
- The sequence is unique and increments correctly.
- A user can associate one or more personnel records.
- A user can upload a DOCX file.
- The DOCX is stored privately and can be downloaded by authorized users.
- An order can be saved as Draft.
- Draft metadata and document can be edited.
- An order can move through approval, signed, released, archived, and revoked states according to permissions.
- Signed and released orders cannot be casually edited.
- Orders can be filtered by number, series, purpose, status, personnel, and dates.
- The original uploaded document and later document versions remain traceable.
- All automated behavior is covered by tests.

## 12. Key implementation decision

Order metadata and documents should remain separate concerns:

- Database fields should contain the searchable order number, series, purpose, dates, status, signatory, and personnel links.
- Document storage should contain the uploaded and generated files.
- Document versions should preserve the history of changes.

This separation keeps filtering and reporting reliable while allowing the document workflow to evolve independently.
