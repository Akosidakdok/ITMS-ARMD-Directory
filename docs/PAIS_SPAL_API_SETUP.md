# PAIS and SPAL API setup

PAIS owns promotion-driven rank and SPAL owns the principal posting for linked personnel. Each application keeps its own database. Use a staging database and staging backends for the first run.

1. Apply the PAIS SQL migration in [supabase/migrations](../supabase/migrations). It expects the existing PAIS personnel, assignment, and promotion schema. In a Supabase environment where these objects already exist, reconcile the migration history before running automated migrations. Run python manage.py migrate in SPAL. The integration migration depends on 0037_dashboard_roster_transfers.
2. Configure PAIS with PAIS_SPAL_ENABLED=true, PAIS_SPAL_SPAL_URL (the SPAL backend base URL), and its server-side SUPABASE_SERVICE_ROLE_KEY. Configure SPAL with PAIS_SPAL_PAIS_URL (the PAIS backend base URL). Set the same PAIS_SPAL_RANK_TOKEN on both backends. Set a different PAIS_SPAL_ASSIGNMENT_TOKEN on both. Use deployment secret stores and HTTPS base URLs. Plain HTTP is accepted only for loopback testing.
3. Provision one reviewed UUID per person on both sides. Store it in PAIS pais_spal.personnel_link with the local personnel_id and in the SPAL PaisPersonnelLink primary key with the local dashboard and/or survey personnel ID. The two SPAL references must belong to the same person. Verify uniformed matches using the original badge strings, including leading zeros. Use reviewed identity matches for NUP and leave their PAIS baseline_rank empty for assignment-only synchronization.
4. For uniformed rank synchronization, review existing PAIS records marked implemented, set baseline_rank to the verified fallback rank before the applicable promotion history, and set baseline_date if known. Set the published_rank, published_date and published_promotion_id to the verified shared starting state if the two apps already agree. Leaving these fields empty queues a rank baseline on the first PAIS scan. Treat existing local Main assignments as part of the posting baseline before provisioning each link.
5. Populate pais_spal.office_map for each permitted pair of SPAL OfficeUnit.code and DashboardUnit.key. Use an empty dashboard_unit_key for a transfer without a dashboard destination. Each entry supplies PAIS unit, sub_unit, and their categories. The implemented SPAL movement supplies the designation and location used as PAIS station. Backdates that would supersede a later current PAIS posting require review.
6. Start both services. PAIS polls its rank outbox and activates due implemented promotions while the backend is running. Schedule python manage.py deliver_pais_assignments in the SPAL environment, for example every five minutes. The command also runs manually. It prints acknowledged and pending counts. Failed deliveries stay queued with a five-minute retry delay. A failed earlier transfer pauses delivery of later transfers for that person so posting history can be applied in order.

PAIS continues to treat saving a promotion with its order reference as recording it as implemented. Pass implemented=false to the PAIS promotion API to stage it, then set implemented=true when implementation is confirmed. Future implemented promotions become current only on or after their Asia/Manila effective date. PAIS keeps the before and after state of linked promotion corrections and deletions.

Confirm both directions using synthetic records before linking real personnel. Check PAIS pais_spal.rank_outbox and pais_spal.assignment_receipt, and SPAL PaisAssignmentOutbox and PaisRankReceipt. Use the existing SPAL transfer workflow for posting changes and the PAIS promotion workflow for rank changes. Direct roster and profile corrections do not publish events. Salary grade synchronization and automatic reconciliation of backdated or preexisting assignment history require a separate policy.
